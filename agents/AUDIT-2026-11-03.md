# Audit: belisoful/prado-meta, 2026-11-03

Scope: everything at `1f7f8a3`, checked against PRADO master `b079b8d1`: `src/`, `config/`,
the tests, CI, the Composer metadata, and the docs.

Method: I read every file. I tested each suspected bug with a script against SQLite (in memory)
and a real PostgreSQL 17 server. MySQL was not running on this machine, so the MySQL findings
are **by inspection** and are marked that way. `composer fulltest` passes, and so does
`composer validate --strict`. Line coverage is 95.1% (235/247).

## Status: all findings addressed (same day, uncommitted at time of writing)

Every finding below is fixed or documented, and has a test. `TEntityMetaModuleDriverTest` runs
on SQLite, PostgreSQL 17 and MySQL 26.7 (via the `META_*_DSN` environment variables), and CI now
runs it against MySQL 8 and PostgreSQL 16. Choices worth knowing:

- **2:** for a guest, reads through the behavior return the default, and writes throw
  `meta_user_guest`. The module API (`$module->getMeta('Guest', …)`) is unchanged.
- **3:** `AllowedClasses` defaults to none. Restoring objects needs `AllowedClasses="*"` or a
  list of classes. The package has no release yet, so no stored data depends on the old default.
- **4:** this is a documentation fix. A table needs a unique (entity, key) index, and WordPress's
  `usermeta` has to gain one first.
- **8:** new rows record their serializer, `p` (PHP) or `j` (JSON). Old `a` rows are read with
  the configured serializer.
- **10:** auto-create on any driver other than MySQL, PostgreSQL or SQLite throws
  `meta_table_create_unsupported`. Writes on such a driver use delete-then-insert inside a
  transaction.
- **13:** booting again replaces the module's own behavior. A behavior of the same name attached
  by other code still makes `attachClassBehavior` throw.
- **14:** MySQL 8.0.19 and later uses a row alias, and MariaDB keeps `VALUES()`. Tables are
  created with `utf8mb4_0900_bin` (`utf8mb4_nopad_bin` on MariaDB, `utf8mb4_bin` before MySQL
  8). Tables that already exist keep their collation. The `VALUES()` and MariaDB paths were not
  run against a real server.
- **16:** `MaxEntityIdLength` (128) and `MaxKeyLength` (191); 0 turns the check off.
- **19:** the cache is dropped on `OnEndRequest`. It has no size cap within a request.
- **20:** the README covers the identifier rule and that `TDbUser` has no `ID`.
- **T4:** php-cs-fixer and PHPStan now check `tests/unit` and `tests/test_tools`. The runtime
  behavior methods are ignored in PHPStan for test files only.
- **T2:** `tests/initdb_mysql.sql` was reused as the local MySQL setup for the driver tests
  rather than deleted.

## Critical

### 1. PostgreSQL does not work with the default settings

`createDbTable()` makes `autoload` a `BOOLEAN` on PostgreSQL. The code then treats it as an
integer:

- `setMeta()` binds `1` or `0` with `PDO::PARAM_INT`. PostgreSQL rejects it:
  `column "autoload" is of type boolean but expression is of type integer` (SQLSTATE 42804).
  **Every `setMeta()` fails.**
- `loadRows()` filters on `autoload <> 0`. PostgreSQL rejects it:
  `operator does not exist: boolean <> integer` (SQLSTATE 42883). **Every first read of an
  entity fails.**

Only `AutoLoadField=''` works on PostgreSQL. CHANGELOG and README both say PostgreSQL upserts
are supported. No test covers this because the suite runs only on SQLite (see T1).

Fix: bind the flag with `PDO::PARAM_BOOL` on pgsql, and compare `autoload = :autoload` with a
bound `true` instead of `<> 0`. This also works on MySQL and SQLite. Add a PostgreSQL test leg.

## High

### 2. All guest visitors share one meta entity

`getUserEntityId()` falls back to the user name. Every guest's name is the manager's guest name
(`Guest` by default), so every anonymous visitor reads and writes the same rows. In the
reproduction, visitor 2 read `'visitor-1 secret'`, which visitor 1 had set. Anything an app
writes for a guest (a cart, a preference) reaches every other guest.

Fix: for an `IsGuest` user, throw on write, or make writes do nothing and reads return the
default. Document which.

### 3. `unserialize()` with no class restriction

`decodeValue()` calls `@unserialize($stored)` without `allowed_classes`. A row with type `a`
whose value names a class creates that class when it is read. The reproduction got a
`stdClass` back from a value written directly in SQL. Getting there needs write access to the
table: another application sharing it, SQL injection elsewhere, or a restored backup. PRADO has
been removing this pattern from its own code (HMAC-checked page state, JSON auto-login
cookies).

Fix: add an `AllowedClasses` property that is passed to `unserialize()`. Restoring objects is a
documented feature, so changing the default has to be weighed against backward compatibility.

### 4. The WordPress `usermeta` compatibility claim is false (by inspection)

README says `TypeField=''` maps the module onto WordPress's `usermeta`. That table has:

- no unique index on `(user_id, meta_key)`, because WordPress allows several values per key. On
  MySQL, `ON DUPLICATE KEY` then never matches, so **every `setMeta()` inserts another row**,
  and `getMeta()` returns whichever row comes back first. On SQLite and PostgreSQL,
  `ON CONFLICT` raises an error because there is no matching constraint.
- no `autoload` column, so `AutoLoadField=''` is also required. README does not say so.

Fix: correct the README. If WordPress support matters, a mode that updates rows in place and
does not rely on a unique index is needed.

### 5. The cache keeps a value after its transaction rolls back

If `setMeta()` runs inside a transaction that later rolls back, the cache keeps the new value
while the table keeps the old one. The reproduction read `cache=new db=old`. PRADO #1441 just
added `TDbTransaction::onRollback`, which is the hook for this.

Fix: when the connection has an active transaction, record which entities were written and
flush them from the cache on `OnRollback`.

## Medium

### 6. `INF` and `NAN` turn into `0.0`

Floats are encoded with `json_encode()`, which returns `false` for `INF`, `-INF` and `NAN`. That
is stored as `''`, which reads back as `(float) '' === 0.0`. This loses data with no error,
whichever serializer is set.

Fix: encode the non-finite values explicitly (for example `INF`, `-INF`, `NAN`), or use
`var_export`/`serialize_precision`.

### 7. The JSON serializer loses data without an error

- `json_encode()` failures (invalid UTF-8, `NAN` inside an array, too deep) return `false`,
  which is stored as `''`. The value just written comes back intact while cached, then as `null`
  after a flush. This was reproduced.
- An object comes back as an object while cached and as an array after a flush (reproduced). The
  docs say JSON does not restore objects, but the cached read does restore them.

Fix: use `JSON_THROW_ON_ERROR`, and turn the error into a `TInvalidDataValueException` with a
message code. In JSON mode, cache the decoded form of what was stored.

### 8. Changing `Serializer` makes existing rows unreadable

Type `a` does not record which serializer wrote the row. After a switch from `php` to `json`,
every existing array or object reads as `null`. This was reproduced.

Fix: give JSON rows their own type code (for example `j`), and read each row by its own code.
Rows that already exist keep `a` and are read as before.

### 9. Auto-create fails on quoted or schema-qualified table names

`ensureSqlIdentifier()` accepts `"post meta"` and `app.post_meta`. The index names are built as
`$table . '_entity_key'`, which produces `"post meta"_entity_key` and
`app.post_meta_entity_key`. Both are syntax errors. Both cases were reproduced.

Worse, `CREATE TABLE` has already succeeded by then. The table is left without its unique
index, and `_tableEnsured` stays true. That brings back problem 4: duplicate rows on MySQL, and
an `ON CONFLICT` error on SQLite and PostgreSQL.

My previous commit added a test that checks these names are accepted. Validation was not the
cause, because before that commit the names were accepted with no check at all.

Fix: build index names from an unquoted, unqualified base name. Also, either create the table
and its indexes in one transaction where the database supports transactional DDL, or reject
such names when `AutoCreateTable` is on.

### 10. Auto-create on other drivers (by inspection)

The `default` case of the `switch` in `createDbTable()` emits `AUTO_INCREMENT` and `MEDIUMTEXT`
for every driver other than SQLite and PostgreSQL. That DDL fails on SQL Server, Oracle,
Firebird and DB2. The delete-then-insert fallback for other drivers is therefore reachable only
with a table made by hand.

Fix: handle `DRIVER_MYSQL` explicitly, and throw a configuration error with a message code for
any other driver.

### 11. `ensureTable()`

- Any `\Exception` from the probe query counts as "table missing". If the database is down or
  the user lacks permission, the module tries `CREATE TABLE`, or reports `meta_table_nonexistent`
  when the real problem is something else.
- `_tableEnsured = true` is set before the probe runs. After a `meta_table_nonexistent` error,
  the next call skips the check and fails with a raw `TDbException` instead. This was
  reproduced.
- On PostgreSQL, a failed probe inside the caller's transaction aborts that transaction
  (`25P02 current transaction is aborted`). This was reproduced.

Fix: set the flag only after a successful probe or a successful create. Detect the table
through `getDbMetaData()` rather than a failing query.

### 12. A write before the first read turns off autoload preloading

`ensureLoaded()` checks `isset($this->_cache[$entityId])`. `setMeta()` creates that entry, so
once an entity has been written, its autoload rows are never loaded in bulk. Every later key
costs a separate query. Results stay correct; this costs performance only. It was reproduced.

Fix: keep a separate "autoload rows loaded" flag for each entity.

### 13. A second `TUserMetaModule` in one process throws

`init()` calls `TComponent::attachClassBehavior('meta', IUser::class)`. That registry covers the
whole process, so a second module, or an application booted again in a long-running worker,
throws `component_class_behavior_defined`. This was reproduced. PRADO's new event-loop and
socket servers make long-running processes more likely. The tests have to detach the behavior
in `tearDown` to avoid exactly this.

Fix: check `IUser`'s class behaviors before attaching, or detach on shutdown, and document that
only one instance is allowed.

### 14. MySQL (by inspection)

- `VALUES(col)` in `ON DUPLICATE KEY UPDATE` has been deprecated since MySQL 8.0.20. The
  replacement is a row alias (`... AS new ON DUPLICATE KEY UPDATE col = new.col`). MariaDB does
  not support the alias, so the choice has to depend on the server.
- With the server's default collation, the `meta_key` column is case-insensitive and ignores
  trailing spaces. `Colour` and `colour` then share one row, but the cache treats them as two
  keys, so the module returns different values depending on what is cached. The created table
  should use `utf8mb4_bin` for the key column.

### 15. The fallback write is not atomic

For drivers without an upsert, `setMeta()` deletes and then inserts outside any transaction. Two
writers at the same time can both delete and then both insert, so one fails on the unique key.
A reader in between sees no row.

Fix: wrap the two statements in a transaction when none is already open.

## Low

16. **Entity IDs and keys are not checked well.** An array entity ID causes a PHP warning,
    which PRADO raises as `TPhpErrorException` (reproduced). An object without `__toString()`
    throws a raw `Error`. Lengths are not checked against `VARCHAR(128)` and `VARCHAR(191)`. In
    non-strict MySQL mode, long keys are truncated and can collide.
17. **Cached objects are shared by reference.** Changing an object after `setMeta()` also
    changes the cached value (reproduced: `x=99`). The database still holds the old value.
18. **A corrupt serialized row reads as `false`.** It looks exactly like a stored `false`
    (reproduced), because `@` hides the failure. Consider logging it.
19. **The cache has no size limit and is never invalidated between processes.** That is fine
    for one PHP request, but it is a stale-data and memory risk under PRADO's long-running
    servers, cron fibers and workers.
20. **The docs leave out the identifier rule** for table and column properties.
    `getUserEntityId()` falls back to the user name for PRADO's own `TDbUser`, so the "survives
    a rename" benefit does not apply to stock PRADO user managers. That is worth stating.

## Tests, CI, packaging, docs

- **T1. Only SQLite is tested.** Line coverage is 95.1%, but the 12 uncovered lines are exactly
  the MySQL, PostgreSQL and other-driver branches, and finding 1 is in them. Unlike
  prado-bayesian, CI starts no MySQL or PostgreSQL service. Add both services and a matrix over
  DSNs.
- **T2.** `tests/initdb_mysql.sql` is a leftover from the package skeleton (`prado_compex_unitest`)
  and nothing uses it.
- **T3. CI is behind the sibling packages.** It uses `actions/checkout@v4` and `cache@v4`
  (siblings use v7 and v6). It has no `permissions: contents: read`, no `concurrency` group,
  and no `dependabot.yml`, even though php-cs-fixer and phpstan are now pinned. There are no
  macOS or Windows jobs. The coverage floor is 90 while actual coverage is 95.1, so the floor
  could be raised to 94.
- **T4.** php-cs-fixer and PHPStan skip `tests/`. PHPStan runs at level 3, the minimum.
- **T5. AGENTS.md's Architecture section is wrong.** It calls `TEntityMetaModule` "the example
  bootstrap module (TPluginModule)" and lists `src/Pages/Example.page`, which does not exist.
  The real bootstrap is `TUserMetaModule`, a `TDbModule`. `TMetaBehavior` is not listed.
- **T6. README and Composer metadata.** Consumers need the asset-packagist repository for
  PRADO's `bower-asset/*` dependencies, but the install section does not say so. `ext-pdo` is
  not declared. `phpdocumentor/shim` is in require-dev, but no script uses it. AGENTS.md says
  to keep it.

## What holds up

- Every value is a bound parameter. Table and column names are now validated as SQL
  identifiers.
- Freezing the configuration with `TInitializedTrait` keeps the cache and the table in step.
- The class-behavior design keeps the module out of serialized users. A test confirms it.
- The package standard checks (class map, message codes, ICU patterns, PSR-4) and the Composer
  install integration test are thorough.
- The ICU error messages render correctly on PRADO master.
